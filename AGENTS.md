# AGENTS.md

This project is the **Sanity CMS edition** of an Astro and Tailwind CSS theme (branch `sanity-cms`). All editable content lives in Sanity and is edited in Sanity Studio. Follow the existing component, schema, query, and styling patterns before adding new code.

## Architecture

- **Content lives in Sanity**, not in the repository. There is no `src/content/` folder and no content collections (`src/content.config.ts` exports an empty object).
- **Studio** (repo root): `sanity.config.ts`, `sanity.cli.ts`, and the `sanity/` folder.
  - Schemas: `sanity/schemaTypes/` (`documents/`, `singletons/`, `sections/`, `objects/`), registered in `sanity/schemaTypes/index.ts`.
  - Studio sidebar: `sanity/studioStructure.ts`. Live preview URL mapping: `sanity/presentation/resolve.ts`.
  - Helpers: `sanity/lib/` (`fields.ts` for `imageField`/`imageArrayMember`/`altField`/`hiddenSectionField`/`languageField`/`sectionGroups`, `languages.ts`, `singletons.ts`, `validation.ts`).
  - Languages come from `src/config/language.json` (shared with the site). Never hardcode language codes.
- **Website data layer**: `src/lib/sanity/`.
  - `env.ts` (env values, `isSanityConfigured`, `visualEditingEnabled`), `client.ts`, `fetch.ts` (`sanityFetch`), `queries.ts` (all GROQ), `data.ts` (typed getters such as `getSiteSettings`, `getNavigation`, `getFooter`, `getHomePage`, `getPage`, `getProject`, `getProjects`, `getServices`), `types.ts`, `image.ts`, `portableText.ts`, `visualEditing.ts` (`dataAttribute`).
  - Components never call the Sanity client directly; they use the getters in `data.ts`.
- **Demo mode**: when `PUBLIC_SANITY_PROJECT_ID` is empty, `sanityFetch` evaluates the same GROQ queries with `groq-js` against `sanity/seed/demo-content.json`. The seed must therefore contain valid data for every query.
- **Seed**: `sanity/seed/demo-content.json` is generated by `scripts/sanity/build-seed.mjs` from the original Markdown content of the `main` branch (via `git show`). Do not hand-edit the JSON; change the generator and re-run it. `npm run import-demo` uploads it.
- **Rendering**: `src/pages/[...lang]/` (`index.astro`, `[page].astro`, `portfolio/[single].astro`), `src/pages/404.astro`. Pages resolve their data from `Astro.params` and `Astro.currentLocale` inside the page body (server mode ignores `getStaticPaths` props).
- **Static vs. preview**: `npm run build` always produces a static site with published content. `SANITY_VISUAL_EDITING=true` (dev) or `npm run build:preview` switches to Astro server output with the Node adapter. Draft-mode endpoints live in `src/sanity-routes/` and are injected by `astro.config.mjs` only in preview mode. `src/middleware.ts` sets `Astro.locals.preview`.
- **Technical config stays in code**: `src/config/config.toml` (domain, sitemap, robots, multilingual switches, Open Graph, head scripts), `src/config/language.json`, `src/config/fonts.json`, `src/i18n/*.json` (small UI labels only), `src/styles/theme.css`.

## Project Structure

- Section components live in `src/layouts/components/sections/` and are mapped in `PageSections.astro`.
- Shared widgets live in `src/layouts/components/widgets/`.
- Cards live in `src/layouts/components/cards/`.
- Global styles live in `src/styles/`; check `base.css`, `components.css`, `safe.css`, and `theme.css` before adding classes or values.
- `src/sections.schema.ts` only holds the `sharedButton` schema used for `CustomButton.astro` props. Content fields are defined in Sanity schemas, and website types live in `src/lib/sanity/types.ts`.

## Section Conventions

A page section is one entry in the `pageSections` array (home page and pages). Adding a section touches all of these:

1. **Schema**: `sanity/schemaTypes/sections/<name>Section.ts` (`type: "object"`). Include `hiddenSectionField()` ("Hide this section") and `sectionGroups` from `sanity/lib/fields.ts`, field descriptions, sensible `initialValue`s, and a preview.
2. **Register it**: import it in `sanity/schemaTypes/index.ts`, add it to the `of` array in `sanity/schemaTypes/objects/pageSections.ts`, and add it to one of the `insertMenu` groups there.
3. **Query projection**: add a `_type == "<name>Section" => { ... }` branch to `sectionsFields` in `src/lib/sanity/queries.ts`. Reuse `imageFields`, `linkFields`, and `portableTextFields`.
4. **Types and mapping**: add a `<Name>SectionData` type and include it in the `SectionData` union in `src/lib/sanity/types.ts`. In `data.ts`, convert `link` values with `toButton()` and `stegaClean` non-text values (see Stega below).
5. **Component**: `src/layouts/components/sections/<Name>Section.astro` taking `content` and `dataSanity` props (put `data-sanity={dataSanity}` on the root element).
6. **Mapping**: add `<name>Section: <Name>Section` to the `components` map in `PageSections.astro`.
7. **Seed**: add demo data in `scripts/sanity/build-seed.mjs`, regenerate `sanity/seed/demo-content.json` (`node scripts/sanity/build-seed.mjs`), and check demo mode renders it.

A new **document type** also needs: a Studio structure entry (`sanity/studioStructure.ts`), language templates if it is per language (`sanity/lib/singletons.ts`), a `locations`/`mainDocuments` entry in `sanity/presentation/resolve.ts`, a query and getter, a route if it has its own URL, and seed data.

## Content And Schema

- Every editable copy, label, link, image, button, list, and option must be a Sanity field. Do not hardcode content in components.
- Reuse existing types and field names: `link` (buttons: `enabled`, `label`, `url`, `openInNewTab`), `seo`, `portableText`, `imageField()` (hotspot + "Alternative text" with a warning, not an error), `menuBadge`, `formField`.
- Write field titles and descriptions for non-technical editors, with an example value. Prefer warnings over errors unless the site breaks without the value.
- Per-language documents have a `language` field. Singletons use fixed ids (`siteSettings`, `homePage-en`, `navigation-fr`, …); never create a second copy.
- Image projection is `{ alt, hotspot, crop, asset->{ _id, url, mimeType, metadata { dimensions, lqip } } }` (`imageFields` in `queries.ts`). Render Sanity images with `SanityImage.astro`.
- Rich text is rendered with `portableTextToHtml` from `src/lib/sanity/portableText.ts`.

## Stega And Visual Editing

- In preview, text fields carry invisible stega characters for click-to-edit.
- In `data.ts`, `stegaClean` (from `@sanity/client/stega`) every enum/option, URL/href, slug, language, form field name/value/type, number stored as string, and all SEO/meta values. `getSiteSettings` is fetched without stega.
- Only human-visible text keeps stega. In components, never derive ids, classes, or comparisons from possibly encoded strings; wrap them in `stegaClean` first.
- Never import `SANITY_API_READ_TOKEN` (`readToken`) into client code. It is server-only and only used in preview mode.

## Styling Rules

- Use mobile-first Tailwind CSS.
- Use the nearest existing Tailwind size and theme token.
- Check `src/styles/theme.css` before adding colors, spacing, radii, or typography values.
- Avoid Tailwind arbitrary values.
- Do not add classes to headings that are already handled by `base.css`, including default font weight, tracking, wrapping, or leading classes.
- Keep heading element classes focused on semantic size variants such as `text-h2`, `text-h3`, or layout spacing only when needed.
- Reuse existing utility classes and component classes from `base.css`, `components.css`, and `safe.css`.
- Do not add default CSS values that already exist in base styles.
- Avoid unused wrappers, duplicated cards, and nested card layouts.

## Component Rules

- Reuse existing components before creating new ones.
- Use `CustomButton.astro` for theme buttons. `data.ts` converts Sanity `link` values to its props with `toButton()`.
- Use `Icons.astro` for icons.
- Use `SanityImage.astro` for images from Sanity and `OptimizedImage.astro` for local images in `src/assets/`.
- Use existing card components where a layout already matches.
- Keep imports clean and remove unused code.
- Prefer static rendering. Add client JavaScript only for real interaction.
- Initialize shared browser behavior through existing global/widget scripts instead of duplicating inline logic.

## Forms And Preline

- Use the theme contact/form components for inputs, selects, radios, checkboxes, and date fields.
- Contact form fields come from the `footer` document (`getFooter` maps them to the `ContactForm.astro` shape). The provider and endpoint come from `siteSettings.contactForm`.
- Use Preline components only through existing project patterns.
- Keep Preline initialization centralized where possible.
- Do not replace theme form classes with raw browser defaults.

## Copy And Theme Shipping

- Write generic product-theme copy that customers can use without replacing a specific brand name.
- Avoid hardcoding the theme name inside schema descriptions, seed content, or section copy unless the file is theme metadata.
- Do not leave placeholders like "Lorem ipsum" unless existing demo content already uses placeholder content intentionally.
- Keep Studio labels, descriptions, and validation messages beginner friendly.

## Environment And Secrets

- All variables are documented in `.env.example`. Public values use the `PUBLIC_` (website) or `SANITY_STUDIO_` (Studio) prefix.
- Never commit `.env`, print tokens, or add secrets to content, code, or docs.

## Verification

- Run `npm run astro-check` after code or schema changes.
- Run `npm run build` for broad changes, routing, data layer, or asset changes. Without a project ID it builds from the demo seed, which is a good check that queries and seed still match.
- After Studio schema changes, validate the schema: `SANITY_STUDIO_PROJECT_ID=<any-id> npx sanity schema validate` (a placeholder ID works; it reads `.env` when the variable is already set there).
- After preview changes, also run `npm run build:preview`.
- Do not commit generated output such as `dist/`, `studio-dist/`, or `.sanity/`.
